当一个尚不明晰、体量超出单次 Agent 会话、且笼罩在迷雾中的想法出现时：从当前位置通往**终点（destination）**的路径尚未显露。Wayfinding 的核心是“探明路径”，而不是盲目向终点冲锋。本技能会在仓库的 Issue 追踪器上绘制一张**共享地图（map）**，随后逐个解决其中的**决策工单（decision tickets）**——每个工单的结论都是一项决策，而非待执行的开发切片——直到整条路线清晰为止。

每次任务探索的终点各不相同，而明确命名终点是绘图的第一步，它决定了后续所有工单的形态。终点可能是一份可供交接与迭代的规格说明、一份在规划启动前需锁定的决策，或一项就地执行的变更（例如数据结构迁移）。地图本身与具体领域无关：无论是工程开发、课程内容还是其他事务，只要形态契合均可适用。

## 只做规划，不直接实施

Wayfinder 默认处于**规划（planning）**阶段：每个工单负责敲定一项决策；当路线完全清晰、在动手实施前已无任何悬而未决的决策时，地图即告完成。当你产生“干脆直接把活干完”的冲动时，通常意味着你已经走到了地图边缘，该进行交接了。如果某次探索确实需要将执行纳入地图本身，可在 **Notes** 中明确覆盖此规则；否则一律只产出决策，不直接产出交付物。

## 按名称引用

每张地图和每个工单都是一个 Issue，因此都拥有自己的**名称（name）**，即其标题。在所有面向人类阅读的内容（对话叙述、地图的 `Decisions so far` 索引）中，必须使用该名称来指代它，切勿只写裸 ID、编号或 slug。一长串 `#42, #43, #44` 极难阅读，而名称能让人一目了然。ID 与 URL 不会丢失：将名称包裹为链接即可，让编号和网址藏在名称*内部*，而不要用它们代替名称。

## 地图（The Map）

地图是本仓库 Issue 追踪器上的单个 Issue，带有 `wayfinder:map` 标签，作为唯一权威产物（canonical artifact）。其下的工单均作为该地图的子 Issue 存在。

地图是一份**索引（index）**，而非存储库。它只列出已做出的决策，并指向承载决策细节的对应工单；每项决策只存在于其所属工单这唯一一处，因此地图从不复述细节，只写一句话摘要与链接。

**地图、子工单、阻塞关系及前沿查询的具体物理承载方式取决于追踪器。** 本仓的追踪器约定见 [`issue-tracker.md`](issue-tracker.md) 中的“Wayfinding 操作约定”一节。

### 地图正文

地图是整张路线图的低分辨率全局视图，每次会话仅加载一次。未关闭的工单**不会**列在正文中：它们是开放状态的子 Issue，直接通过查询获取。

```markdown
## Destination

<抵达这张地图终点时的形态：本次探索所要寻找的规格说明、决策或变更。一到两行即可；每次会话在挑选工单前都要先对齐此目标。>

## Notes

<所属领域；每次会话都应查阅的技能；本次探索的常驻偏好约定>

## Decisions so far

<!-- 索引区：每个已关闭工单占一行，足以判断相关性即可，需要细节时点击链接深入查看 -->

- [<已关闭工单标题>](link): <一句话结论摘要>

## Not yet specified

<!-- 见“战争迷雾”：属于范围内但尚无法写成工单的迷雾；随前沿推进逐步毕业为正式工单 -->

## Out of scope

<!-- 见“超出范围”：明确排除在终点之外的工作；永久关闭，永不毕业 -->
```

### 工单（Tickets）

每个工单都是地图的**子 Issue（child issue）**；追踪器的 Issue ID 即其唯一标识。工单正文就是待解决的问题，体量控制在单次 100K token 的 Agent 会话可消化的范围内：

```markdown
## Question

<本工单需要敲定的决策或需要查明的调研问题>
```

每个工单都带有 `wayfinder:<type>` 标签，取值为 `research`、`prototype`、`grilling`、`task` 之一（见[工单类型](#工单类型)）。`wayfinder:` 系列标签是地图及其工单唯一允许携带的标签，切勿混用 `ready-for-agent` 等分诊标签：它们代表决策，而非实现任务。

会话在开展任何工作**之前**，必须**先认领（claim）**工单，即将其指派（assign）给推进该地图的开发者，以便并发会话自动跳过。该指派人（assignee）本身*就是*认领标记：开放且未指派的工单即为未认领状态。

阻塞关系使用追踪器**原生**的依赖关系（dependency）：这一点至关重要，因为只有原生依赖才能在追踪器 UI 中*直观渲染*出当前前沿，让人类无需打开地图就能看清哪些工单可接手。仅当追踪器不支持原生阻塞时，才退回正文约定。当一个工单的所有阻塞项均已关闭时，它即处于**未阻塞（unblocked）**状态；**前沿（frontier）**指所有开放、未阻塞且未认领的子工单，代表已知世界的边界。

工单答案不写回正文，而是在解决时单独记录（见[推进地图](#推进地图)）。解决工单过程中产出的资产应从 Issue 中链接出去，不要直接整段粘贴进正文。

## 工单类型

每个工单要么属于 **HITL**（人机协同，与能够自主表达意见的人类共同完成），要么属于 **AFK**（由 Agent 独立驱动完成）。HITL 工单只能通过真实的人机实时交互来解决；Agent 绝不能替人类作答（如果一个 grilling Agent 自问自答，就已经违反了这一原则）。

- **Research（AFK）**：查阅文档、第三方 API 或本地知识库等资料，提取决策所依赖的客观事实。由子代理按 [`research.md`](research.md) 执行调研。当需要当前工作目录之外的知识时使用。
- **Prototype（HITL）**：通过制作廉价、粗糙、一次性、可立即运行的最小验证原型（大纲、粗稿、桩代码或独立 Demo）来提高讨论保真度，供人类直观反馈，并将原型作为资产链接到 Issue（不合入主分支）。当核心问题是“应该长什么样”或“应该如何表现”时使用。
- **Grilling（HITL）**：对话追问。这是默认类型。务必同时遵循 [`grilling.md`](grilling.md) 与 [`domain.md`](domain.md)。
- **Task（HITL 或 AFK）**：在能够做出*决策*之前必须先完成的手工前置工作——此时既无决策可做、也无需原型或调研，但若不做完它就无法推进讨论。例如注册某个服务以评估其 API、开通访问权限、迁移数据以观察其形态等。这是唯一“做事”而非“决策”的工单类型，它存在的意义是解除某项决策的阻塞，而不是交付最终目标。Agent 能独立完成的则自主推进（AFK）；否则向人类提供一份精确的操作清单（HITL）。工作完成后即告解决；答案中需记录完成了什么以及后续工单依赖的产出事实（如凭据位置、新 URL、行数等）。

## 战争迷雾（Fog of war）

地图是*刻意*保持不完整的：不要去绘制你尚且看不见的东西。在现有工单之外，是**战争迷雾（fog of war）**：你能预感到前方还存在某些决策与调研，但由于它们依赖于尚未解决的问题，眼下还无法钉死。每解决一个工单，就会驱散它前方的迷雾，把如今已经足够清晰的部分逐一“毕业（graduate）”为新工单，直到通往终点的道路完全清晰、不再有遗留工单为止。

地图中的 **Not yet specified** 区域用于写下这种模糊的远景：疑似存在的问题、日后需要回访的领域。它是通往*终点*途中尚未被探索的前沿：这里的内容全部属于范围之内，只是尚不足以写成工单。能写多细就写多细、多粗就写多粗；它同时也能作为路标，让协作者看清本次探索的前进方向。

**放入迷雾还是建为工单？** 判断标准在于你*现在*能否把问题精确陈述出来，*而非*你现在能否回答它。

- **建为工单**：问题已经足够清晰具体，即便当前仍被阻塞、尚不能动手处理，也应建为工单。
- **留在 Not yet specified**：问题还无法表述到那种清晰度。不要提前把迷雾强行切分成工单大小的碎片：迷雾的粒度比工单更粗，当前沿推进到那里时，一块迷雾可能会毕业成多个工单，也可能根本不需要建工单。

**Not yet specified** 必须排除已经敲定的内容（`Decisions so far`）、已经存在的活跃工单，以及超出范围的内容（见下一节）。

## 超出范围（Out of scope）

迷雾永远只朝向*终点*聚集。终点划定了本次探索的边界，因此越过终点的事项属于**超出范围（out of scope）**：它不是迷雾，不应留在 **Not yet specified** 中，而是归入地图独立的 **Out of scope** 区域——记录那些你经深思熟虑后决定排除在*本次*探索之外的工作。决定它落在这里的是“范围”，而非“清晰度”。

超出范围的事项永远不会毕业（前沿在终点处即止步），只有在重新划定终点时它才可能回归——而且届时应作为一次全新的探索，而非旧地图的延续。

将某项工作划出范围是一种定界行为，而不是路线上的前进步骤。当一个已存在的工单被发现其实位于终点之后（绘图时误划入，或在解决其他工单后暴露出来）时，应**直接关闭它**（已关闭的工单毫无疑问已退出前沿），并在 **Out of scope** 区域留下一行记录：简要说明内容及为何超出范围，并附上该已关闭工单的链接。它不应进入 **Decisions so far**，因为后者只记录实际走过的路线，范围边界并不是路线中的一步。

## 调用方式（Invocation）

共有两种模式。无论哪种模式，**每次会话绝不解决超过一个工单**（`research` 工单除外）。

### 绘制地图（Chart the map）

用户带着一个尚不成形的想法发起调用。

1. **命名终点。** 结合 [`grilling.md`](grilling.md) 与 [`domain.md`](domain.md)，钉死这张地图最终要通往何处：是某份规格、某项决策还是某次变更。终点决定范围，因此必须最先敲定。
2. **测绘前沿。** 再次进行追问（grilling），这一次采用**广度优先（breadth-first）**：横向铺开覆盖整个问题空间，而不是在某一条线上深挖，以此浮现出所有待定决策以及当前即可着手的第一批步骤。**如果此过程没有发现任何迷雾**（通往终点的路径已经一目了然，整个旅程小到单次会话就能完成），则说明你不需要地图。停下来询问用户希望如何继续。
3. **创建地图**（打上 `wayfinder:map` 标签）：填好 `Destination` 与 `Notes`，`Decisions so far` 留空，将迷雾粗略写入 **Not yet specified**。
4. **为当前可明确陈述的部分创建工单**，作为地图的子 Issue；然后在**第二轮扫描（second pass）**中连接阻塞边（Issue 需要先拿到 ID 才能相互引用）。交叉引用也应在第二轮使用真实 ID 补全：占位符 `#<n>` 可能会自动链接到无关 Issue。连线完成后，工单自然分为“前沿”与“被阻塞”两类；其余尚无法明确陈述的内容留在迷雾中，即 **Not yet specified** 区域。
5. **派发调研子代理。** 针对刚创建的每一个 `research` 工单，分别启动一个拥有全新上下文窗口的子代理并按 [`research.md`](research.md) 并行完成调研；将调研结果保存在一次性分支 `research/<name>` 上，并在工单中附上指向上下文位置的链接。推送该分支但不要创建 PR：该分支永远不会被合并。
6. 停止：绘制地图本身就是一次会话的工作量，本阶段不手动解决任何工单。

### 推进地图（Work through the map）

用户传入一张地图（URL 或 Issue 编号）发起调用。工单参数是**可选的**：若未指定，由你（而非用户）挑选下一个待解决的决策。

1. 加载**地图**：只读取低分辨率的地图总览，不要一口气加载每个工单的正文。
2. 选择工单。若用户已指定则采用之；否则按顺序选取前沿中的第一个工单。**认领它**：在开展任何工作前先将工单指派给自己。
3. 按照其 `wayfinder:<type>` 标签所指明的类型来解决它（见[工单类型](#工单类型)）。务必读取标签而不仅仅是正文：正文中从不标明类型。**按需放大（Zoom as needed）**：仅在需要时拉取相关工单或已关闭工单的完整正文；并查阅 `## Notes` 中点名的每一项技能/文档。如有疑问，同时遵循 [`grilling.md`](grilling.md) 与 [`domain.md`](domain.md)。
4. 记录解决结果：将答案作为**解决评论（resolution comment）**发布到工单下，**关闭**该 Issue，并在地图的 `Decisions so far` 中**追加一条上下文指针**。
5. 补充新浮现的工单（先创建再连线）；将本次答案使之变得足够清晰的那部分迷雾“毕业”为新工单，同时把已毕业的内容从 **Not yet specified** 中清除，确保它只以新工单的形式存在。如果答案揭示出某个工单（当前工单或其他工单）其实位于终点之外，则应**将其划出范围（rule it out of scope）**，而非当作路线上的节点去解决。如果该决策使地图上的其他部分失效，应同步更新或删除对应工单。

用户可能会并行推进多个未阻塞的工单，因此要预期其他会话可能同时在编辑追踪器。
